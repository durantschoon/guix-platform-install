Guix System on Oracle Cloud's free tier

A whole Linux machine whose entire configuration is one file you can read, on a VM that costs nothing per month. This page explains how — it is a description of the flow, not a button. It deploys nothing and asks you for nothing.

Read this first

Parts of this flow are not finished yet. The published, ready-to-import image does not exist, so today you still need someone with a working Guix machine to build one. The piece that would remove that requirement — installing your SSH key from Oracle's instance metadata — has been run on real instances and does not work yet; it is being debugged in the open. The status section at the bottom says exactly which parts, and this page does not pretend otherwise anywhere above it.

What this is

Guix System is a Linux distribution where the machine is described by a file rather than assembled by a sequence of commands you have to remember. You write down the services, users and packages you want; guix system reconfigure makes the machine match. Every change becomes a new generation you can boot back into from the GRUB menu, so a bad change is a reboot rather than a reinstall.

Oracle Cloud's Always Free tier includes VM shapes that stay free indefinitely rather than for a trial period, which makes it a reasonable place to keep a small always-on machine. The relevant shape here is VM.Standard.E2.1.Micro: 1 OCPU, 1 GiB of RAM. That is enough to run the system and to do a guix pull, but the 1 GiB is the constraint you will actually feel — the image ships a swap file specifically so that a reconfigure has somewhere to spill.

Oracle cannot boot an installer ISO the way a laptop can; it only accepts a disk image you upload. So there is no interactive installer in this flow at all. The system is built as a QCOW2 image from oracle/image/oracle-image.scm, imported as a custom image, and launched. Everything personal happens afterwards, over SSH.

What you need

  • An Oracle Cloud account. Signing up requires a credit card for identity verification; Always Free resources are not billed to it.
  • An SSH key pair. You will paste the public half into Oracle's console. If you do not have one: ssh-keygen -t ed25519, then use ~/.ssh/id_ed25519.pub.
  • A terminal that can run ssh. Nothing else is installed on your machine — you do not need Guix locally for the console path below.
  • About 20 minutes, most of it waiting on the image import.
Expect this, it is normal

Always Free capacity runs out. Launching VM.Standard.E2.1.Micro in a busy region frequently answers "Out of host capacity". This is not a mistake you made and not something a retry loop fixes reliably. The usual remedies are to try a different availability domain in your region, or to use the ARM VM.Standard.A1.Flex shape, which is also Always Free and often has room. Oracle's free tier is genuinely free, and the price of that is that you are last in line for hardware.

The steps

This is the console-only path: everything up to the SSH login happens in Oracle's own web console, which is the only thing that ever sees your Oracle credentials.

  1. Get the image

    The intent is that you import a published, generic Guix image straight from a URL. That image is not published yet, so there is no URL to give you and this page will not invent one.

    Until it exists, the image has to be built once by someone who already runs Guix, using oracle/README.md, and uploaded to an Object Storage bucket you can read. The build is a single declarative file and the whole upload/import/launch sequence is scripted there.

  2. Import it as a custom image

    In the OCI console: Compute → Custom Images → Import image, pointing at the object in Object Storage. Two fields are not optional:

    • Image type: QCOW2
    • Launch mode: Paravirtualized — it has to match the BIOS/MBR layout the image is built with. Choosing Native (UEFI) gives you an instance that never boots.

    Import is asynchronous; wait for the image to reach Available. This is the slow part.

  3. Launch, pasting your public key

    Create an instance from that custom image on shape VM.Standard.E2.1.Micro, in a VCN with a public subnet — the console's Create VCN with Internet Connectivity wizard makes one correctly. Assign a public IP.

    Paste the contents of your .pub file into the console's Add SSH keys box. That box writes the key into the instance's metadata, and a small service in the image reads it at boot and installs it. This is what lets one published image serve everybody instead of one build per person.

    Then open port 22 in the subnet's security list, which is not open by default.

    The metadata key service is the part that has never been exercised on a live instance — see status.

  4. Log in

    on your machine 
    ssh guix@<public-ip>

    The user is guix. Password authentication is disabled by design, so this succeeds or it does not — there is no password to fall back on. If it does not, Oracle's serial console (Instance → Console connection) works: the image deliberately puts GRUB and a login prompt on ttyS0 for exactly this moment.

  5. Make it yours

    What you are logged into is deliberately bare: no git, no editor beyond nano and mg, bash as the login shell. One command turns it into your machine — that is the next section.

The one command

Run this on the instance, over that SSH session:

on the instance 
wget -qO- https://raw.githubusercontent.com/durantschoon/guix-platform-install/main/postinstall/recipes/add/personal-config.scm \
  | guile --no-auto-compile -s /dev/stdin

Nothing has to be installed first. A fresh Guix System already has wget, guile and nss-certs; the script installs git itself, into your user profile rather than the system, so it takes seconds instead of a rebuild.

It asks for your configuration repository's URL, sets up an SSH key and pauses while you register that key with GitHub or wherever your repository lives — no script can paste a key into a web page for you, so it stops there deliberately instead of failing later at git clone with Permission denied (publickey). Then it clones, shows you a plan, and runs each step with a yes/no prompt and the exact shell command echoed first.

Piping a script into guile like this is safe here for a specific reason: every prompt in it reads from /dev/tty, not stdin — stdin is the script itself, arriving down the pipe.

Bring your own config

What that command runs is not decided by this repository. It is decided by a file named guix-personal.scm at the root of your own configuration repository. Your dotfiles repo declares what a new machine needs; the installer stays generic. Nothing personal — no URL, no username, no Makefile target — is hardcoded anywhere in the installer.

guix-personal.scm 
(personal-config
  (version 1)
  (name "dot_files")
  (description "Durant's personal configuration")

  ;; Installed into the user profile before any step runs.
  (requires "git" "gnu-make" "zsh")

  ;; Optional: copied to ~/.config/guix/channels.scm, with confirmation.
  (channels "channels.scm")

  (steps
    (step (name "links")
          (run "make set_up_links")
          (description "Symlink dotfiles into $HOME")
          (default? #t))
    (step (name "home")
          (run "make apply")
          (description "guix home reconfigure")
          (default? #t))
    (step (name "keyd")
          (run "make setup-keyd")
          (description "Key remapping; physical machines only")))

  (notes "Log out and back in for the login shell change to take effect."))

Steps marked (default? #t) are the ones "the one command" runs; the rest are offered and default to no. Unknown keys are a hard error rather than being silently ignored, because a typo'd (require "git") that is quietly dropped becomes a step failing on a machine you are reaching over a serial console.

Write the file before you need it, and check it on a machine you can actually debug:

on your workstation, in a checkout of this repo 
guile --no-auto-compile -s postinstall/recipes/add/personal-config.scm \
      --plan ~/dot_files

Prints the full plan and exits non-zero if the contract is malformed. --init ~/dot_files will generate a starting point from your existing Makefile.

The full specification — every key, what is required, what the failure modes are — is in docs/PERSONAL_CONFIG_CONTRACT.md.

Status: what is verified and what is not

This section exists so the rest of the page can be read at face value. Two things this flow depends on are not done, and both are load-bearing for the console-only path above.

Verified?What
yes Building the image, the local QEMU smoke test, uploading, importing, and launching an instance with sshd answering on its public IP. Done end-to-end on 2026-08-08 with a key baked into the image.
no The published generic image does not exist yet. There is no URL to import from, and this page does not link to one. Someone with Guix installed must build and share the image until it is published. This is step 2 of the roadmap.
no The metadata SSH key service has never run on a live instance. Pasting your key into the console's Add SSH keys box is supposed to be what gets you in at step 3 above. The service is implemented and the "no metadata available" path is covered by the local QEMU test — but QEMU has no instance metadata service, so the path that actually matters has only been reasoned about, not observed. Until one live launch confirms it, assume you may need a key baked into the image instead.

Everything downstream is gated on that second item. If a launch with a metadata-only key lets you ssh guix@<ip>, the rest of the roadmap is unlocked; if it does not, the serial console log lines beginning metadata-ssh-keys: name the failure.
